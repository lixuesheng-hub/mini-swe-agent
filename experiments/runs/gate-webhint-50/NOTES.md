# 实验：submit gate 全量 50 题（webhint 提示词 + gate）

**假设**：模型提交时强制"在干净 checkout 上应用补丁并重跑它自己跑过的测试"，能让"补丁改了一半就交卷"的实例
改到通过，且不弄坏本来能过的题。
**唯一变量**：在 `swebench_webhint.yaml`（提示词版）之上开启 `enable_submit_gate.yaml`：
`GatedAgent` + `GatedDockerEnvironment`（默认关闭，不加载时与基线逐字节一致）。
**数据**：verified-mini 50 题，与 baseline / `retrieval-prompt-50` / `__rep2` 同一批题，可配对。

## 结果

| 指标 | baseline | prompt rep1 | prompt rep2 | **gate（本次）** |
|---|---:|---:|---:|---:|
| resolved | 30/50 = 60% | 41/50 = 82% | 42/50 = 84% | **44/50 = 88%** |
| Wilson 95% CI | [46,72] | [69,90] | [71,92] | **[76%, 94%]** |
| 与基线配对 | — | 12 赢 / 1 输 p=0.0034 | 13 赢 / 1 输 p=0.0018 | **14 赢 / 0 输 p=0.0001** |
| 步数中位 / 均值 | 34 / 46 | 28 / 37 | 29 / 45 | 34 / 44 |
| 回归实例（回归数） | 6（11） | 5（9） | 3（7） | 4（8） |
| 检索实例 | 4 | 45 | 49 | 48 |

### 与 prompt 版的对比（稳定口径）

- prompt 稳定集（rep1∩rep2 = 38 题）→ gate **独有 6 题**：`11815`、`12308`、`12406`、`10673`、`8548`、`9229`；
  **gate 挂但 prompt 稳定过的：0 题（零损失）**。
- 其中 3 题（`10673`、`8548`、`9229`）**是被 gate 拦住后修好并通过**的——gate 直接救回；
  另 3 题（`11815`、`12308`、`12406`）是 prompt 版随机翻转失败的题，本次通过。
- 注意 `10673` 在 rep1 曾陷入 259 次重复 grep 耗尽 250 步，本次被 gate 拦两次后正常通过。

### gate 行为统计

| 指标 | 值 |
|---|---|
| 触发 gate 的实例 | 17 / 49（35%） |
| 总拒绝次数 | 31 |
| 拒绝原因构成 | `own_tests` 31 次；`patch_applies` / `syntax` **0 次**（模型补丁都能干净应用、无语法错误） |
| 拦截分布 | 2 次拒绝 14 例、1 次拒绝 3 例（max_attempts=3，第 3 次无条件放行） |
| 被拦实例步数中位 | **69**（vs 未拦实例 25）；最贵 134 步（`8548`） |
| 被拦实例最终通过 | **15/17 = 88%** |
| 未触发 gate 实例通过率 | 29/32 = 91% |

**gate 判断与 harness 的一致率**：被拦的 17 题里 15 题最终 resolved（gate 的"你还没验证好"判断正确）；
2 题仍失败（`10435`、`8269`）——gate 判断正确但模型能力不足以修好。
gate 放行后 harness 判挂的仅这 2 例，没有"gate 放行但补丁根本不对"的大面积失真。

## 结论

1. **gate 带来净提升且零损失**：44/50 = 88%，比 prompt 稳定集 38/50 多 6 题，比单次 rep1/rep2 多 3/2 题；
   在 50 题规模上 baseline→gate 为 14 赢 0 输（p=0.0001）。
2. **机制解释**：35% 的实例第一次提交时"自己跑过的测试还红着"，gate 把它们打回；其中 15/17 最终修好。
   被拦实例步数中位从 25 涨到 69——这就是代价：**用 2.7 倍步数换 +6 题**（约 +15pp）。
3. **gate 拦的是"未验证的提交"，不是"能力不足"**：`patch_applies` 和 `syntax` 一次都没拒过，
   说明模型补丁形式上是好的；失败的 2 题（`10435`、`8269`）是理解型失败，gate 帮不上。
   这修正了 TODO T2 原先的假设措辞：8269/8475 的失败**不是**"急着交卷"能概括的——
   8475 本次通过，8269 被拦 1 次后仍失败。
4. **成本**：被拦实例平均多 40+ 步。若按 API 计费，需与 +6 题的收益权衡；对包月通道只是时间成本。

## 局限

- **单次 run**：44/50 尚未复跑；prompt 版两次之间就有 7 题翻转，gate 的 +6 题需要 rep2 确认
  （尤其那 3 题"随机翻转后通过"的 11815/12308/12406 可能翻回去）。
- `sphinx-9461` **卡死**：容器跑了 8 小时无新轨迹（模型 API 请求挂起），批量被手动终止，
  该题按 50 题口径计为失败（44/50）。这是稳定性问题，不是 gate 逻辑问题——但说明当前
  缺少 per-call watchdog（阶段 4 早停/超时策略的直接证据，加上 rep1 的 10673 死循环共 3 例）。
- 开卷前提不变：48/50 实例检索了上游，gate 提升中仍混有 lookup 成分。

## 踩坑（实现 bug，均已修）

1. 提交命令实际是 `cd /testbed && echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt`，
   前缀导致 gate 的字符串匹配失效 → 首轮冒烟 gate 完全没触发。
2. 批量 runner 硬编码 `ProgressTrackingAgent(DefaultAgent)`，忽略配置的 `agent_class`
   → `GatedAgent` 从未生效（测试目标列表永远为空）。已改为 `make_progress_tracking_agent(base)` 工厂。
3. coarsening 保留了文件级目标（模型先跑整个 `test_build_linkcheck.py`），gate 重跑整文件
   >300s 超时 → 每次都假拒。改为"同文件有 node 级目标时只保留 node 级"。
4. 自定义环境以 dotted path 给定时 `get_sb_environment` 不注入 `image` → 改为按基类推断。
