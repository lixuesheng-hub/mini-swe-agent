# 实验报告：SWE Agent 脚手架与检索策略

> 一句话结论：**同一模型、同一基准上，决定成败的是"何时、以何种方式获取外部信息"与"提交前是否自检"**——一句零代码检索提示把基线 60% 推到 82%，再加一层提交前 gate 推到 88%（14 赢 0 输，p=0.0001）。

- 基准：SWE-bench verified-mini，50 题（django 25 + sphinx 25）
- 框架：mini-swe-agent 2.4.6，默认配置（`swebench.yaml`，step_limit 250，yolo）
- 判分：官方 harness（`swebench` 5.0.2，docker，本地执行，不消耗模型额度）
- 日期：2026-10

<!-- TLDR:START -->
基线 **30/50 = 60%**（95% CI 46–72%）；单次结果不足以判定小幅改进。
- **提交前 gate：44/50 = 88%（+28pp，配对 14 赢 0 输，p=0.0001）**，比提示词版的稳定集（38/50）多 6 题、零损失；代价是被拦实例步数中位 25→69
- **提示词版两次全量复现：41/50=82% 与 42/50=84%（合并 83/100）**，对基线配对均显著（p=0.003 / 0.002）；步数中位 34→28，检索实例 4/50→45–49/50
- 两次 run 间 7 题单题翻转（交集 38/50=76%，并集 45/50=90%）：点值有噪声，显著性稳健
- 工具版全量（`github_fetch`，无提示）：36/50 = 72%（+12pp），配对 p=0.070 → 未显著；"给工具"≠"会用工具"
- 失败分三类：能力型 / 边界噪声型 / 未验证提交型——gate 只能治第三类，且拦的是"未验证"而非"能力不足"（`patch_applies`/`syntax` 零拒绝）
- 稳定性：3 例模型退化（10673 重复 grep 259 次、7985/9461 空转耗尽），其中 9461 容器挂死 8h → 需 per-call 超时/早停

## 1. 方法

**为什么用这套基准**：SWE-bench 有客观判分（跑测试，而不是人看输出），才能把"感觉变好了"变成"确实变好了"；verified-mini 只需约 5 GB 镜像、保持与全量 verified 相近的难度分布，适合高频迭代。

**噪声控制**：
- 每个 run 记录 `metrics.json`（步数、截断次数、重复命令、检索实例数）与 harness 报告（F2P/P2P 明细）；
- 汇总表统一给出 **Wilson 95% 置信区间**，并统计 `PASS_TO_PASS` 回归数作为细粒度质量信号；
- 每个变体一次只改一个变量，功能代码默认关闭（`extra_tools` 为空时与基线逐字节一致）。

**指标定义**：
| 指标 | 含义 |
|---|---|
| resolved | FAIL_TO_PASS 全部通过且无 PASS_TO_PASS 回归（官方口径） |
| 回归数 | 新弄坏的旧测试数量（区分"接近正确"与"完全跑偏"） |
| 检索实例数 | 轨迹中出现网络请求（curl/wget/urllib + URL）的实例数 |
| 步数 | assistant 消息数（≈ API 调用次数） |

**怎么判断"这个改动有没有用"**（仪表盘 `vs baseline` 列的口径）：

1. **先看区间，不看单点**：每个 resolved 率都带 Wilson 95% 区间；n=50 时区间宽约 ±13pp，
   所以"60% → 70%"这种量级本身不足以支撑结论。
2. **只用同任务集的 run 互相比较**：`vs baseline` 仅在同一批题上计算。n=2 探针与 50 题基线
   任务集不同，显示「—（任务集不同）」——它们的区间宽达 [34%, 100%]，不可比。
3. **重叠比例作快速判断**：

   | 重叠宽度 ÷ 较窄区间宽度 | 判读 |
   |---|---|
   | `0%` | 不重叠，可称显著 |
   | `< 20%` | 边缘（再差 1–2 题就分开） |
   | `20–50%` | 部分重叠，说不准 |
   | `> 50%` | 明显重叠，视为无差异 |

   实测参考：基线 30/50 的区间是 [46%, 72%]；**新版要到 43/50（+13 题）才完全不重叠**，
   40/50 时仍重叠 25%。
4. **正式结论看差值区间**：重叠判据偏保守——实测 40/50 时两区间仍重叠 25%，但差值区间
   `[+2.0, +36.4]pp` 已不含 0。因此报告里写"显著"时以**差值区间是否跨 0** 为准
   （同题配对可用 McNemar）。

## 3. 三个发现

### 3.1 单题存在随机翻转，基线数字本身有噪声

同一配置重跑两个最难实例：

| 实例 | 第一次 | 第二次 |
|---|---|---|
| `sphinx-8638` | ❌ 100 步 | ✅ 133 步 |
| `sphinx-8056` | ❌ 100 步 | ❌ 46 步 |

粗估单次 resolved 的随机误差 **±3–5 个百分点**。含义：消融差异小于 2–3 题时不应下结论。

### 3.2 失败不是一类事——至少三种

| 类型 | 代表实例 | 特征 |
|---|---|---|
| 能力/理解型 | `8056` | 多个模型多次尝试均卡在同一目标测试 |
| 边界噪声型 | `8638` | 所有模型最终都能解，单次结果不可靠 |
| 早提交/回归型 | `8269`、`8475` | 14–19 步就提交，目标测试部分通过却引入多个回归 |

这解释了为什么"只看 resolved 率"会掩盖信息：加 `回归数` 后，`glm-5.3` 那唯一的失败立刻显示为"还弄坏了 1 个旧测试"。

### 3.3 检索策略是决定性变量（**探针结论，n=2**）

探针设计：固定模型（doubao-lite）与框架，只改"检索能力的呈现方式"，在 `8056` + `8638` 两题上对比。

| 变体 | 8056 | 8638 | 检索次数 | 步数 |
|---|:---:|:---:|---:|---:|
| 基线（无提示、无工具） | ❌ | ❌→✅ | 1（被动、晚） | 100 / 100 |
| **prompt 提示**（提示先查 issue/PR） | ✅ | ✅ | 5 | **21** |
| 独立工具 `github_fetch`（无提示） | ✅ | ❌ | 4（仅 8056） | 55 / 98 |
| glm-5.3 | ❌ | ✅ | — | 84 / 66 |
| kimi-k3 | ✅ | ✅ | — | 43 / 54 |
| deepseek-v4-pro | ✅ | ✅ | — | 42 / 75 |
| deepseek-v4.1-flash | ✅ | ✅ | — | **21** / **31** |

读法：
1. **同一模型同一题**，只加一段检索提示：100 步失败 → 21 步成功，且步数与最强模型持平；
2. **工具不会自动被用**：`github_fetch` 无提示时，模型在 8638 上一次都没调用（0 次）→ "给工具"≠"会用工具"，需要提示引导；
3. **基线并非完全不检索**，而是 4/50 实例检索过且多为"卡住后的被动查询"（这 4 个仅 1 个成功，未检索的 46 个成功率 63%）。

### 3.4 全量验证：工具版 +12pp，但仍在噪声内（配对 p=0.070）

把同样的工具变体推到**全量 50 题**（唯一改动仍是注册 `github_fetch`，提示词保持原样）：

| 指标 | 基线 | 工具版全量 | 变化 |
|---|---:|---:|---|
| resolved | 30/50 = 60% | **36/50 = 72%** | **+12pp（+6 题）** |
| 95% CI | [46%, 72%] | [58%, 83%] | **重叠 58%** → 明显重叠，不显著 |
| django / sphinx | 18 / 12 | 20 / 16 | +2 / +4 |
| 回归实例（回归数） | 6（11） | 4（8） | 略降 |
| 步数中位 | 34 | 32 | 略降 |
| 检索实例 | 4/50 | **22/50** | 大幅上升 |

逐题：新解决 7 题，新失败 1 题（`sphinx-9229`）。

**关键读法**：

1. **+12pp 不能称为提升**。按区间判据，50 题规模需 +13 题（43/50）才不重叠；
   本次是"方向为正但未超出噪声"的典型样本。
2. **工具确实被用起来了**：63 次调用、22 个实例（44%），远高于基线自发检索的 4/50。
3. **但"用过工具"组成功率更低**（64% vs 79%）：这是**难度混淆**——题目越难模型才越可能去查，
   不代表工具导致失败。想拆开因果需要同题配对比较，目前数据不支持。
4. **早提交型失败没被改善**：`sphinx-8269`（25 步）、`sphinx-8475`（40 步）仍失败，
   各只用 1 次工具 → 工具教会了"查资料"，但没教会"别急着交卷"。

### 3.5 全量验证：提示词版 +22pp，同题配对显著（p=0.003）

把 n=2 探针里效果最强的变体（**不加工具，只在提示词里加一段"先用 curl 查上游 issue/PR"**）推到全量 50 题
（`swebench_webhint.yaml`，`extra_tools` 为空）：

| 指标 | 基线 | 工具版 | **提示词版** |
|---|---:|---:|---:|
| resolved | 30/50 = 60% | 36/50 = 72% | **41/50 = 82%** |
| Wilson 95% CI | [46%, 72%] | [58%, 83%] | [69%, 90%] |
| vs 基线（新过/新挂） | — | 7 / 1 | **12 / 1** |
| McNemar 双侧 p | — | 0.070 | **0.0034** |
| 步数中位 / 均值 | 34 / 46 | 32 / 46 | **28 / 37** |
| 回归实例（回归数） | 6（11） | 4（8） | 5（9） |
| 截断 | 22 | 34 | 16 |
| 检索实例 | 4/50 | 22/50 | **45/50** |

配对明细：提示词版新解决 12 题（11848/11885/11964/12273/12308；sphinx 10323/7590/7748/8056/8548/8638/9230），
新失败 1 题（`django-11815`）。提示词版 vs 工具版为 7 赢 2 输（p=0.18）。

**读法**：

1. **探针结论在全量成立且显著**：同模型同题，只加一段提示词，60% → 82%，步数反而更少。
   这是本项目第一个通过同题配对检验的变体（区间重叠判据只显示 15% 的"边缘"，正式结论以差值配对为准，见 D02）。
2. **机制是"让检索成为默认早期动作"**：检索实例 4/50 → 45/50；而不给提示的工具版只有 22/50 自发用工具。
   零代码的行为引导强过给一个等待被发现的工具。
3. **提示词优于工具的直接比较尚不显著**（p=0.18），只能说方向一致。
4. **早提交型失败依然没被修复**：8269（21 步、5 次 curl）、8475（18 步、4 次 curl）在提示词版仍失败——
   检索让模型查得更多，但拦不住草草交卷，提交 gate 是独立的必要干预（T2）。
5. **开卷**：45/50 实例查阅了上游，提升中相当部分是 lookup 成功，不能等同于独立解题能力提升。

**异常**：`sphinx-10673` 在第 6 条命令后把同一条 grep 重复执行 259 次直到 250 步耗尽（空补丁），
贡献了仪表盘 230 次重复命令中的 214 次；它全程只有 1 次 curl，属模型退化的单实例病态循环，
不是检索/限流所致。该题工具版为 resolved，是提示词版唯一明确输给工具版的案例，也是需要 rep2 复跑的理由。

### 3.6 rep2 复跑：点值稳定（82% / 84%），显著性两次复现，run 间噪声量化为 ~7 题

同配置重跑一次全量 50 题（`runs/retrieval-prompt-50__rep2`）：

| 指标 | rep1 | rep2 |
|---|---:|---:|
| resolved | 41/50 = 82% | 42/50 = 84% |
| vs 基线配对 | 12 赢 / 1 输，p=0.0034 | 13 赢 / 1 输，p=0.0018 |
| 步数中位 | 28 | 29 |
| 回归实例（回归数） | 5（9） | 3（7） |
| 空补丁（250 步耗尽） | 1（10673） | 1（**7985**，另一题） |
| 重复命令 | 230（214 在 10673） | 9（正常） |

- 两次都过 38 题、都挂 5 题、**7 题单题翻转**（rep1↔rep2 配对 p=1.00，无系统差异）；
  合并 n=100 为 **83/100 = 83%**；保守口径（两次交集）76%，乐观口径（并集）90%。
- 关键个案：8056/8638 两次都过；10673 在 rep2 正常通过（证明 rep1 的循环是随机退化而非提示词副作用）；
  11815 rep1 挂 rep2 过（随机翻转）；**8269/8475 两次都挂**，早提交型失败稳定存在；7985 两次都挂并在 rep2 耗尽步数。
- 经验噪声：单题翻转约 ±7/50（比早先 ±3–5pp 的粗估略大），但**对基线的显著优势两次独立复现**，结论稳健。
- 每个 run 有 1 题陷入 250 步空转耗尽（位置随机），为阶段 4 早停 policy 提供了直接证据。

### 3.7 提交前自检 gate：44/50 = 88%，14 赢 0 输

在提示词版之上叠加 gate（`GatedAgent` + `GatedDockerEnvironment`，默认关闭）：模型发出提交命令时，
先把补丁应用到一份干净 git worktree，再重跑**它自己轨迹里跑过的测试**；不过则打回继续修（≤3 次）。

| 指标 | baseline | prompt rep1 | prompt rep2 | **gate** |
|---|---:|---:|---:|---:|
| resolved | 30/50 = 60% | 41/50 = 82% | 42/50 = 84% | **44/50 = 88%** |
| Wilson 95% CI | [46,72] | [69,90] | [71,92] | **[76%, 94%]** |
| 与基线配对 | — | 12/1，p=0.0034 | 13/1，p=0.0018 | **14/0，p=0.0001** |
| 回归实例（回归数） | 6（11） | 5（9） | 3（7） | 4（8） |

**与提示词版的稳定口径对比**：prompt 稳定集（rep1∩rep2 = 38）→ gate **独有 6 题**
（11815/12308/12406/10673/8548/9229），**gate 挂但 prompt 稳定过的 0 题**；其中 3 题
（10673/8548/9229）是被 gate 拦住后修好并通过的。

**gate 行为**：17/49 实例触发（35%），31 次拒绝，**全部来自 `own_tests`**——`patch_applies` 与 `syntax`
零拒绝，说明模型补丁形式都能用，gate 拦的是"没验证"而不是"写错了"。被拦实例步数中位 **69**（未拦 25）。
被拦的 17 题中 15 题最终 resolved（88%），2 题仍失败（10435、8269，能力型）。

**结论**：gate 带来净提升且零损失，代价是约 2.7 倍步数（仅对 35% 提交过不掉的实例）。
但这是**单次 run**，prompt 版两次间就有 7 题翻转，+6 题需 rep2 确认。

**稳定性事故**：`sphinx-9461` 容器跑了 8 小时无新轨迹（模型 API 请求挂起），批量被手动终止，
按 50 题口径计失败。连同 rep1 的 10673 重复 grep 259 次、rep2 的 7985 耗尽 250 步，共 3 例模型退化/挂起
→ 当前缺 per-call 超时与早停（阶段 4 的直接证据）。

### 3.8 三类失败的重新划分（gate 提供的新证据）

gate 的 `patch_applies` / `syntax` 检查**一次都没拒过**，31 次拒绝全部来自 `own_tests`，
说明失败不是"补丁写不出来"，而是：

| 类型 | 特征 | 能否用 gate 治 |
|---|---|---|
| 未验证提交型 | 补丁形式完整，但模型自己跑过的测试还红着就交 | ✅ 主要靠它（15/17 修好） |
| 能力型 | 多轮修正后目标测试仍不过（`8269`、`10435`） | ❌ 需更强模型/更多信息 |
| 退化/挂起型 | 重复同一命令耗尽步数（`10673`）、API 挂起 8h（`9461`） | ❌ 需 per-call 超时 + 早停 |

## 4. 负结果与局限（重要）

- **单次全量仍有 run 间噪声**：提示词版 41/50 是单次结果（±3–5pp 随机翻转），
  且新挂的 11815、病态循环的 10673 都可能在复跑中翻转；结论方向有 p=0.003 支撑，但 82% 这个点值需要 rep2/rep3 收敛。
- **n=2 探针不能当全量结论**（已部分兑现）：检索探针的两个变体都已跑全量——提示词版显著（§3.5）、工具版不显著（§3.4）。
- **开卷问题**：部分成功来自查阅上游 PR/issue，属于"开卷"能力。报告与评分应区分 **lookup 成功** 与 **独立解出**；混合统计会高估模型能力。
- **失败尝试**：
  - `deepseek-v4.1-flash-economy` 在 agent 真实负载（长 system prompt + 工具历史）下单次请求挂死、并发触发服务端突发保护，**不可用于 agent 场景**；
  - `w=4` 并发会更快撞上套餐 5 小时滚动配额，故统一 `w=2`。
- **相关性≠因果**：工具版里"用过 github_fetch"组成功率更低（64% vs 79%），
  统计上属难度混淆（难题才触发检索），不能据此说工具无效或有害；需同题配对分析。
- **未验证**：`run_test` 精准测试工具、提交自检 gate（8269/8475 已在全部三个变体中失败，优先级最高）、best-of-N 的实际收益只有假设与设计；
  上下文压缩已有数据决定暂缓（D08）。

## 8. 结论与下一步

**能说的**：基线 60%（CI 46–72%）；失败分三类（未验证提交 / 能力 / 退化挂起）；
**检索时机是决定性变量**——一句提示词两次全量 60%→82%/84%，配对 p=0.003/0.002；
**提交前 gate 把它们推到 88%（14 赢 0 输，p=0.0001），且零损失**；工具不做行为引导时提升不显著；上下文压缩暂无必要。
**不能说的**：提示词版与工具版有显著差异（p=0.18）；单次 82%/88% 是精确点值（prompt 两次间 7 题翻转）；
提升等于独立解题能力（48/50 开卷）；gate 的 +6 题已稳定（仅单次 run）。

下一步（按优先级）：
1. **gate 全量 rep2**：+6 题（相对 prompt 稳定集）中 3 题是随机翻转后通过，需复跑确认；
2. **per-call 超时 / 早停**：9461 挂死 8h、10673 重复 259 次、7985 耗尽 250 步 —— 3 例退化，纯稳定性收益；
3. `run_test` 单项消融（纯效率）；2B 检索工具泛化可砍。
